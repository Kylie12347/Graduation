# 关柜、支付后锁柜与页面流转

## 行为

整个系统仍为纯软件仿真。电脑管理台点击“关柜生成清单”即产生模拟关门信号，后端记录door_open=false，并将会话由OPEN转为REVIEW。小程序通过2.5秒轮询发现状态变化，展示关柜后的清单、待确认商品和支付入口。用户停留在首页时，首页同样能检测未完成会话已关门，自动进入该会话结算页。

用户仍需明确核对购物清单并点击支付，不会自动扣款，也不会跳过异常商品确认。关闭后柜体保持占用，门锁状态显示未锁定；会话已非OPEN，因此不能继续正常取放。

模拟支付失败：保留UNPAID、柜体占用和未锁定状态，可重试。后端若发现柜门仍打开，拒绝支付且不创建支付流水。

模拟支付成功：订单PAID、销量增加、door_open=false、locked=true、清除active_session在同一事务完成；任何异常都会回滚，不会单独放行柜体。重复成功请求沿用原幂等逻辑，不重复记账。

购物页依据后端实际返回的PAID自动退出到首页，清除扫码绑定和轮询。首页显示“已支付并锁柜”，不再保留上一次的直接开柜按钮；下一次购物需要重新扫码。若支付已成功但响应丢失，后续会话轮询也能检测PAID并返回首页。

历史订单入口携带readOnly=1，已支付订单详情仍可查看，不会被完成购物的自动跳转打断。未支付订单经历史入口支付成功后同样返回首页。

取消并归还商品时也将门关上并锁定，释放柜体。

## 数据与界面

新增cabinet_locks(cabinet_id,locked)表，启动时自动创建，不修改或删除既有订单库存。旧柜无记录时默认显示锁定，第一次开柜时补建未锁定记录。

会话详情增加doorOpen、cabinetLocked。柜体列表及消费者货架接口提供locked，管理台显示柜门和门锁两种状态。开柜后locked=false，关柜待支付时仍false，成功支付/归还取消后true。

首页扫描绑定在开柜成功后消耗。这里的扫码绑定只是前端交互状态，并非生产级一次性门禁凭证；后端仍通过用户令牌、会话及柜体占用判断是否允许操作。

## 验证

实际运行21项后端规则及Spring TestContext/MockMvc/H2测试、14组小程序逻辑测试，全部通过。新增测试覆盖关柜状态、失败支付不释放、成功锁柜、门开拒付、归还取消锁柜、付款后页面跳转、后台支付完成轮询、历史订单保留和扫码绑定清理。五个页面WXML通过微信内置wcc编译，代码差异空白检查通过。

Java在本机关闭依赖JAR时有路径权限诊断，使用生成的类文件和Spring TestContext实际执行测试；不宣称本机Maven verify通过。未执行真实微信支付、真实门锁或手机扫码，本项目不接实体硬件。

## 应用与验收

应用同步脚本后，停止并重新启动IDEA后端，再重新编译小程序，无需删除数据库。开柜、电脑端取商品、电脑端关柜后，小程序应在约一个轮询周期后显示结算清单。先尝试模拟失败，确认后台柜体仍占用；再模拟支付成功，确认后台显示已关闭/已锁定、柜体可用，小程序自动返回首页，首页恢复扫码开柜按钮。订单列表中仍能查看刚才的订单。
