# 测试与答辩演示

## 自动化验证

```powershell
cd backend
mvn test
```

`FusionEngineTest`验证7个规则场景；`ShoppingIntegrationTest`验证购物闭环、取出再放回、失败支付重试、幂等支付、异常确认、归还取消、权限隔离、参数/柜门校验、库存预警补货和并发开柜。测试使用独立内存数据库，不修改演示文件数据库。

可选Node静态检查：在仓库根目录运行`node scripts/check-miniprogram.cjs`。它验证JS语法、JSON配置、页面四件套及WXML绑定的方法是否存在，不代替微信开发者工具编译与真机测试。

GitHub Actions会在推送时运行Maven验证和前端静态检查。工作流通过不意味着真实硬件验证或真实微信支付验证，本系统没有这些模块。

| 取放抵消 | 取2放1 | 净购买1件 |

| RFID漏读 | 同上，开启漏读 | 候选不唯一，待确认 |

| 失败重试 | 先模拟失败，再模拟成功 | 一条失败尝试、一条成功尝试，营业额只增加一次 |

## 建议答辩讲解顺序

1. 说明研究对象：纯软件多源感知仿真，不声称实现真实视觉识别。
2. 展示消费者小程序与电脑仿真面板的分工。
3. 运行正常购物，展示重量→RFID→视觉三个步骤。
4. 开启漏读与等重场景，展示系统保留不确定性，消费者核实后结算。
5. 展示失败支付重试、成功订单统计和库存预警。
6. 打开`FusionEngine`解释为什么它没有访问仿真答案的能力。
7. 用库存公式解释物理取放与销售记账的区别，以及人工错认的审计差异。

## 可如实说明的局限

本项目每次观察一种SKU，不支持同时取多种商品的组合识别；RFID模拟聚合数量而非真实射频传播；视觉是差异开关；匿名登录在重启后失效；待处理订单保持占柜；尚无退款、盘点审批、生产账号体系。论文结果只能说明这些仿真规则和参数下的行为。

如果开展准确率实验，应固定操作序列和异常参数，将`simulation_actions`作为独立标准答案，比较原始`result_json`，人工确认后的订单不能代替算法原始输出。不要把手动确认结果统计成自动识别成功。
