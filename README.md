# 柜见：基于微信小程序的无人售货柜多源感知仿真与结算系统

纯软件毕业设计项目。没有实体柜、传感器、真实摄像头、图像识别模型或真实支付。

消费者通过微信小程序选择柜体并开柜，电脑管理台模拟商品取出、放回及关柜。后端依次分析**重量 → RFID → 视觉差异**，生成购物清单；消费者处理异常、确认清单后执行模拟支付。管理台统计已售件数、柜内剩余、补货提醒和当天流水。

## 目录与技术

```text
backend/         Java 17 + Spring Boot 3.5.7 + JDBC后端，IDEA导入pom.xml
  src/main/java/cn/graduation/cabinet/
    FusionEngine.java       不读取操作答案的三步规则融合
    SimulatorService.java   取放仿真和人为异常数据生成
    ShoppingService.java    会话、清单、支付、取消
    AdminService.java       商品、库存、补货及上海时区营业统计
  src/main/resources/static/ 原生HTML/CSS/JS管理台，与后端一起启动
  src/test/                  规则测试和业务集成测试
miniprogram/     原生微信小程序，直接导入此目录
docs/            设计解释、语言基础、接口和演示步骤
scripts/         静态检查及Windows启动脚本
.github/         GitHub Actions自动验证
```

数据库默认使用文件型H2，第一次启动生成演示柜体和商品，不需要预先安装MySQL。提供可选MySQL配置。管理台无需安装Node或执行npm。

## 1. IDEA启动后端及管理台

1. 安装JDK 17、Maven 3.9或更高版本。
2. IDEA选择“打开”，选择`backend/pom.xml`并作为项目打开。
3. Project SDK设置为17，等待Maven下载依赖。
4. 运行`cn.graduation.cabinet.CabinetApplication.main()`。
5. 浏览器访问 <http://127.0.0.1:8080/>。
6. 管理员默认演示密码：`admin123`。可通过`ADMIN_PASSWORD`环境变量修改。

命令行启动：

```powershell
cd backend
mvn spring-boot:run
```

打包和测试：

```powershell
cd backend
mvn verify
java -jar target/smart-cabinet-1.0.0.jar
```

数据文件默认在启动工作目录下的`data/`。IDEA的Working directory建议设置为`backend`，确保多次启动使用相同数据库路径。不要同时运行两个实例占用同一H2文件。

## 2. 微信开发者工具导入

1. 打开微信开发者工具，选择“导入项目”。
2. 项目目录选择`miniprogram`；使用自己的测试AppID，或本地游客模式。
3. `project.config.json`已将`urlCheck`设为false。如工具仍提示域名问题，在本地详情中勾选“不校验合法域名、web-view域名、TLS版本以及HTTPS证书”。
4. 先运行后端，再点击“编译”。默认接口为`http://127.0.0.1:8080/api`。
5. 首次会自动创建匿名演示身份。身份令牌保存在本地缓存，有效12小时；服务重启后令牌失效，需要重新登录。旧订单仍保存在数据库，可在管理台查看。

真机调试需要将`miniprogram/app.js`中的`baseUrl`换成电脑局域网IP，同时后端设置`SERVER_ADDRESS=0.0.0.0`，手机和电脑处于同一网络。首次联调推荐使用开发者工具模拟器。此演示未接真实微信登录和微信支付。

## 3. 完整演示

1. 小程序输入`CAB001`并申请开柜。
2. 管理台进入“虚拟售货柜”，点击“刷新会话”并选择当前会话。
3. 默认异常配置全部关闭，点击可乐“取出”。重量减少330克，RFID识别可乐，视觉无差异，自动确认。
4. 再取出可乐一瓶，再放回一瓶，清单最终只保留一瓶。
5. 点击“关柜生成清单”。小程序自动刷新后确认清单。
6. 先点击“模拟支付失败”，再点击“模拟支付成功”。失败不增加销量，成功只记一次。
7. 管理台“经营概览”刷新后查看营业额、商品销量、实际库存、柜体流水和小时趋势。

异常案例：可乐与橙汁都设为330克，开启“RFID漏读”后取出可乐，重量无法区分，两者成为候选并标记待确认。关柜后在小程序核实商品、方向及数量，再确认清单。开启“视觉发现差异”也会进入待确认。

取消案例：未付款时若有商品在柜外，消费者直接取消会得到归还提示。管理台执行“全部归还并取消”，会实际恢复物理库存，记录归还流水，再取消订单。

## 4. 库存和统计口径

| 字段 | 含义 | 改变时机 |
|---|---|---|
| `on_hand` | 虚拟柜中实际剩余件数 | 取出减少、放回/补货增加 |
| `held` | 当前会话实际取出但未结算的数量 | 由仿真记录汇总，仅管理端可见 |
| `sold` | 累计已支付销量 | 模拟支付成功时增加一次 |
| `supplied` | 初始库存+累计补货数量 | 初始化/补货 |
| `discrepancy` | supplied−on_hand−sold−held | 非零提醒人工确认可能与物理状态不一致 |

支付时不再次扣减`on_hand`。营业额只统计`PAID`订单，按`paid_at`落在上海时区当天的范围汇总。付款失败、待支付、取消不计入营业额。预警条件为在售商品`on_hand <= threshold_qty`。

## 5. 业务边界

- 每次仿真操作一种SKU、1—10件，可连续取放不同商品；同一会话最多1000次操作。
- 重量、RFID均采用一次操作对应一个观测窗口。RFID模拟的是标签前后集合差汇总出的SKU数量变化，并非读取真实硬件。
- 视觉仅返回“有差异/无差异”，不判断商品类别，不训练模型。
- 融合器只读取`Signal`和商品标称信息；不接收仿真请求、商品操作答案、订单或真实库存。
- 视觉“无差异”不能排除所有错误；两种重量相近商品如果RFID也发生一致误报，仍可能错误确认。这属于简化规则的已知局限，应在实验中如实分析。
- 人工确认是用户输入，原始融合结果不被覆盖。管理台库存差异用于事后审计，不反向提供给算法答案。
- 匿名演示登录和单管理员密码用于本地联调，不是完整生产账号体系；默认仅监听127.0.0.1。
- 正在购物/结算的柜体禁止补货，有未完成会话时禁止修改商品资料。

## 6. 可选MySQL

使用MySQL 8，先建立UTF-8数据库`graduation`，设置环境变量后启用配置：

```powershell
$env:DB_USERNAME='root'
$env:DB_PASSWORD='你的数据库密码'
$env:DB_URL='jdbc:mysql://localhost:3306/graduation?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai'
mvn spring-boot:run '-Dspring-boot.run.profiles=mysql'
```

相同`schema.sql`由Spring初始化。项目自动测试使用H2；MySQL配置需要在你的MySQL环境中另行联调。
