# 柜见：无人售货柜多源感知仿真与结算系统

本项目为毕业设计演示系统。小程序模拟重量、RFID 和视觉输入，后端负责柜体会话、感知融合、运营审核、库存和模拟付款。管理台提供二维码、开关柜对照、订单和经营统计。

## 启动

1. 使用 JDK 17 或 21，在 IDEA 中导入 `backend/pom.xml` 并运行 `cn.graduation.cabinet.CabinetApplication`，工作目录设为 `backend`。默认服务地址为 `http://127.0.0.1:8081`；管理台默认密码为 `admin123`，可通过 `ADMIN_PASSWORD` 修改。
2. 用微信开发者工具导入根目录的 `miniprogram`，在本地联调设置中关闭合法域名校验。小程序 API 地址在 `miniprogram/app.js`。手机真机不能访问电脑的 `127.0.0.1`：局域网联调需让服务监听 `0.0.0.0`，将小程序 API 地址改为电脑局域网地址，并按所用真机调试方式配置网络权限。正式发布应使用 HTTPS 和备案的合法请求域名。
3. 默认用 H2 文件数据库，无需创建库。升级时会创建新表，不重置已有商品、库存和订单。已有旧版未结会话可从管理台“柜体与开关柜审核”归还并结束。

## 配置视觉大模型

在 IDEA 的后端运行配置中设定 `VISION_API_KEY` 与 `VISION_MODEL` 后重启。选用账户实际可访问、同时支持图片输入及结构化输出的模型；默认接口为 `https://api.openai.com/v1/responses`，可以通过 `VISION_API_URL` 指向兼容 Responses 接口的服务。配置只保存在服务端。提交照片会发送至所配置的模型服务；答辩请使用商品照片。

模型按时间戳读取多帧图片，只收到该柜商品名称和图片，不读取 RFID 或重量。模型有效结果只包含商品名称与净取出数量；看不清、接口失败、没有配置或照片不足时，普通商品进入运营审核，不编造识别结果。

## 答辩演示

1. 管理台打开“柜体与开关柜审核”，用小程序首页“扫码开柜”扫描目标柜二维码。小程序显示该柜名称和编号并进入“仿真”。管理台二维码旁的“查看此柜的会话”只显示该柜记录。当前二维码是普通柜体二维码，应从小程序内扫。若要在微信相机外部一扫就打开小程序，需要在微信平台配置普通链接二维码或生成带 `cabinetId` 启动参数的小程序码；小程序已支持读取 `cabinetId` 和 `scene`。
2. 系统启动后自动补齐校园一至六号柜（CAB001–CAB006）。后台查看各柜二维码，小程序首页点「附近售货柜」查看同一份柜体列表。已有未完成会话时不能再开另一台柜，同一柜重复扫码复用原会话。
3. 仿真页三个板块：录入前后重量（误差加在关柜读数上）；设置每枚 EPC 开关柜是否读到；按顺序添加 2–6 张照片。相册照片时间戳取导入顺序，支持调整帧序；建议拍一张开柜前、一张取放中和一张关柜后。误读演示可让另一个 SKU 的标签在关柜快照里消失。仿真页上传观测，不传预选购物清单。
4. **普通商品一致**：RFID 和视觉的 SKU 与数量一致时，小程序弹出模拟付款；无须消费者选择商品。**冲突**：例如让可乐 EPC 消失，照片展示拿橙汁，关柜后消费者只看到“等待运营人员核对”。在管理台选本次会话，对照重量、RFID 和照片后填入橙汁数量及理由；小程序自动刷新并弹出付款信息。
5. **特殊商品**：在商品资料开启“唯一重量候选优先”，录入标称重量并补货。重量减少与某个单 SKU、某一数量的理论重量相差不超过 `max(20 克, 理论重量 × 3%)`，且没有多个单 SKU 候选、没有多商品观测时，可直接进入付款。重量只是优先识别依据，遇到多个候选仍按普通规则或交给运营人员。
6. 运营确认之前不扣实物账面库存；系统决定购物清单后占用本柜库存和对应标签，模拟付款成功后增加销量、登记付款并锁柜。付款失败可重试，不重复扣库存。管理台可按柜体查看销售并横向比较；订单可按柜体、状态、结算方式筛选，交易详情用表格展示。

测试：在 `backend` 执行 `mvn test`；在项目根目录执行 `node scripts/check-miniprogram.cjs` 与 `node scripts/test-miniprogram.cjs`。原 `docs` 中早期仿真流程说明只用于历史对照。
